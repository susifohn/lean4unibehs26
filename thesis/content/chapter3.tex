\section{Systems of Logic}

In classical logic, statements (=Propositions) are either true or false. No test or proof is needed whether a proposition is true or false. E.g. having a proposition $A$ the disjunction $A \lor \neg A$ is always true without showing which side of the disjunction holds. The Law of the Excluded Middle (LEM) holds. \\

On the other side, intuitionistic logic
rejects the LEM. Claiming $A \lor \neg A$ requires to prove at least one side of the disjunction namely $A$ or $\neg A$.\\
Proving $\exists \alpha : P(\alpha)$ requires a witness for $\alpha$ and an algorithm (or program) to compute $P(\alpha)$. A theorem in intuitionistic logic implies being a theorem in classical logic but not in the opposite direction. In general a tautology in classical logic is not a theorem in intutionistic logic.\\

Why this matters? Intuitionistic logic requires a constructive proof that an object exists and this construction suits as an anlgorithm or program to generate such object. As a consequence, a program in lean 4 or other proof assistants can be used as a proof and vice versa. \cite{web:intuitionistic_logic}

\section{$\lambda$ Calculus}
Invented by Alonzo Church 1933 \todo{add ref}. He was also a Supervisor of Alan Turing. Church treated functions as black boxes with no
internal state, means pure functions. On the other side, Turing looked at functions using the Turing Machine,
and states are crucial there. [Ref Graham Hutton, Lambda Calculus - Computerphile].\\

In the $\lambda$ calculus three things exists: 
\begin{enumerate}
    \item Variables, like $x,y$
    \item Abstraction, a way of building functions
    \item Application, applying functions to their arguments
\end{enumerate}


The $\lambda$-calculus consists of a precise notation to investigate functions.


\[
\underbrace{\lambda x_1.\lambda x_2}_{\text{arguments}}
.\underbrace{M}_{\substack{\text{function}\\[2pt]\text{body}}}
\]

where $x_i$, for $i \in \mathbb{N}_{>0}$ are the function arguments and $M$ is telling how the return value is calculated. For example the identity function
$$\lambda x.x$$

For function application, the input values are appended as follows

$$(
\lambda x.x) \;a
$$

returning $a$ in this case. Or in the case of two arguments $x,y$ and two input values $a,b$
$$
(\lambda x.\lambda y.M) a \: b
$$

The three parts of the $\lambda$-calculus variables, abstraction and application can be formulated as a grammar as follows
\[
M ::= x \mid \lambda x.M \mid M\,M
\]

With this simple notation,  we can encode True and False, NOT, AND and any function we want, including recursion and it follows that it is Turing complete. This fact is known as the Church–Turing thesis.\cite{web:lambda_calc}\\


So far, nothing is known about $x$ and the return value of such functions. Therefore  

\subsubsection{The simply typed $lambda$-calculus}
assigns a type to every expression. Using the notation $(value : Type)$, we have for example

$$
(\lambda x.x : \alpha \to \alpha)
$$

or

$$
(\lambda x.\lambda y.y : \alpha \to \beta \to \beta)
$$

The type $\alpha \to \beta$ is the type of a function taking a value of type $\alpha$ and returning a value of type $\beta$. \\

To infer the type of a valid term, we need rules. Let $\Gamma$ be the list of all assumptions, aka context. $\Gamma,x:\alpha$ denotes the extension of $\Gamma$ with the assumption that $x$ is of type $\alpha$.  The simply typed $\lambda$-calculus provides the following rules for variables, abstraction and application:

\[
\begin{array}{c}
\displaystyle
\frac{x : \alpha \in \Gamma}
     {\Gamma \vdash x : \alpha}
\quad\textsc{Var}
\\[2em]
\displaystyle
\frac{\Gamma, x : \alpha \vdash e : \beta}
     {\Gamma \vdash \lambda x.e : \alpha \to \beta}
\quad\textsc{Abs}
\\[2em]
\displaystyle
\frac{\Gamma \vdash f : \alpha \to \beta
      \qquad
      \Gamma \vdash a : \alpha}
     {\Gamma \vdash f\,a : \beta}
\quad\textsc{App}
\end{array}
\]

What is the Trusted Code Base of Lean?

One of Lean's core design approaches is that \textbf{one does not 
need to trust Lean's implementation} in order to trust the proofs 
it produces. Proofs can be verified using independent checkers, 
as described in more detail in the section 
\href{https://lean-lang.org/doc/reference/latest/find/?domain=Verso.Genre.Manual.section\&name=validating-proofs}
{``Validating a Lean Proof''} of the Lean Reference Manual.

Thus, it is sufficient to trust the soundness of the checker used 
to validate the proof output. This basis of trust, i.e., the 
source code of the checker(s) being used, is commonly referred 
to as the \textit{Trusted Code Base (TCB)}. Multiple independent 
checkers can be employed to further increase confidence.

Relying on independent checkers as the TCB covers many of Lean's 
core applications, particularly those in which the proof itself 
is the main product:

\begin{itemize}
    \item Mathematical theorems.
    \item Verification of existing algorithms, protocols, or hardware.
    \item Verification of software written in other programming 
    languages and transformed into Lean statements using tools 
    such as \href{https://github.com/AeneasVerif/aeneas}{Aeneas}.
    The tool in question may introduce additional assumptions 
    concerning how the Lean statements relate to the original 
    software. These assumptions consequently become part of the TCB.
\end{itemize}

An extended use case of Lean, which also entails an extended TCB, 
arises from combining Lean's roles as a theorem prover and as a 
programming language. Examples include:

\begin{itemize}
    \item Executing verified Lean code as native binaries.
    \item Using the \texttt{native\_decide} tactic, which is tracked 
    as an additional axiom for transparency.
\end{itemize}

In these cases, the TCB is extended to include the Lean compiler 
(written in Lean), the Lean runtime (written in C++), and the 
code-generation backend (LLVM by default), as well as any other 
external code linked into the program.

Standard hardening techniques can be employed to increase 
confidence in these components, particularly when combining 
verified and unverified code. In this context, see also the 
\texttt{LEAN\_MI\_SECURE} CMake configuration option, which 
provides allocator hardening for Lean versions 4.31.0 and later.
